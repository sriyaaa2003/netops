# NetOps: ML-Based Network Log Anomaly Detection

Course assignment for Cloud Provisioning and Deployment / The Business Case for Cloud Computing.

## 1. Description of the software
Network test rigs produce a lot of log lines tagged INFO, WARN, ERROR or CRITICAL. Most of it is normal, and the few components that are getting worse are buried in it. Fixed rules like "alert after N errors" do not work well because every component has its own normal behaviour.

This project uses an Isolation Forest. For each batch of logs it counts the severities per component and flags the components that look different from the rest of the batch. It needs no labelled data.

It is made of four parts:
- **log-service** (Node.js, Express): parses raw log lines into records, stores them in Postgres and has a REST API.
- **anomaly-service** (Python, Flask): pulls recent logs from log-service over REST, builds severity counts per component, runs the Isolation Forest, stores the flagged components and has a REST API.
- **frontend** (static HTML served by nginx): generates sample logs, submits them, triggers the analysis and shows the flagged components. It is the only part a browser talks to.
- **Postgres:** stores the logs and the anomalies.

The logs are generated by the frontend, so the demo can be repeated on demand.

## 2. Software architecture design

```
                       +---------------------------+
   Browser  ---------->|   frontend (nginx)         |  LoadBalancer - the only
                       |   static HTML/JS + reverse |  externally reachable
                       |   proxy at /api/*          |  Service in the cluster
                       +-----------+---------------+
                                   |  ClusterIP-only from here on
                    +--------------+---------------+
                    v                               v
        +------------------------+        +---------------------------+
        |  log-service (Node)     |<------|  anomaly-service (Flask)   |
        |  POST/GET /logs         |  GET   |  POST /analyze            |
        |  GET /logs/:id          |  /logs |  GET /anomalies           |
        |  GET /health            |        |  GET /health              |
        +-----------+-------------+        +-------------+-------------+
                    |                                    |
                    +-----------------+------------------+
                                     v
                          +-----------------------+
                          |  Postgres (1 replica)  |
                          |  logs, anomalies tables|
                          +-----------------------+
```

- nginx is the single public entry point and proxies `/api/*` to the backend services.
- Services find each other by name through Kubernetes DNS, for example `http://log-service:4000`.
- anomaly-service calls the log-service REST API to fetch recent logs before fitting the model.
- Each service writes only its own table in Postgres.
- Database credentials come from a Kubernetes Secret and environment variables.
- log-service, anomaly-service and Postgres have no external Service.

## 3. Benefits, challenges, and security
**Benefits**
- No labelled training data is needed.
- The model refits on every batch, so "normal" follows whichever components are reporting.
- Each service scales and fails on its own, which I checked by load testing log-service.

**Challenges and fixes**
- Small batches give noisy counts, so anomaly-service refuses batches under a minimum size.
- Postgres may not be ready when the other services start, so both retry the database connection, and readiness probes keep them out of service until it works.
- nginx used to resolve backend names only once at startup, which could crash-loop the frontend. A templated nginx config now resolves them again on every request.

**Security**
- Database credentials are stored in a Kubernetes Secret and read with `secretKeyRef`.

## Tech stack
Node.js, Express, Python, Flask, gunicorn, scikit-learn (Isolation Forest), PostgreSQL, nginx, Docker, Kubernetes.
